## What this simulation is

You are the tester on a one-day **QA sprint** for **GENKI Wardrobe**, an e-commerce streetwear store (the live [Sandbox](/sandbox) checkout). The increment is a **GENKI hoodie checkout** with a discount code. Leadership wants evidence, not vibes: ISTQB-style cases, a real bug report, a SQL oracle, and a small Playwright spec.

Pass by completing **four phases** in the form at the bottom. A valid submission unlocks **Claim Your Certificate**.

## Outcome

After this capstone you will have practiced the same loop as a junior on a squad: plan from a story, hunt in a buggy UI, confirm persistence with SQL, and automate one smoke journey.

<Info title="Do not repair the Sandbox">
The GENKI checkout contains **seeded defects on purpose**. Report them. Do not "fix" overlap or totals in the product code.
</Info>

## The sprint story

```text
Story GENKI-88 — Apply a merch promo at GENKI hoodie checkout
As a shopper, I want to enter a discount code of 5 to 10 characters on checkout
so that a valid campaign code reduces my GENKI hoodie total.

Acceptance criteria
- Codes with length 5 through 10 (inclusive) are accepted for format checks.
- Length 4 or less, and length 11 or more, are rejected before pricing.
- A recognized code (example SAVE20) must apply at most once.
- Invalid payloads to POST /api/checkout return 400 Bad Request.
- Failed payments persist orders.order_status = Failed.
```

ISTQB lens: this is **black-box** design on the code field (see [BVA](/courses/foundation/02-test-design-techniques)), then **confirmation** in UI, data, and automation.

## Phase 1 — Test planning (ISTQB)

Write **at least three** critical test cases for the GENKI hoodie discount **length** rule using **Boundary Value Analysis**.

The valid partition is length 5 through 10. Boundaries that matter:

| Length | Partition | Typical expected (format) |
| --- | --- | --- |
| 4 | Invalid — below min | Reject / 400 / validation error |
| 5 | Valid min | Format accepted (pricing may still fail if the code is unknown) |
| 10 | Valid max / Boundary | Format accepted |
| 11 | Invalid — above max | Reject |

Paste **one case per line** into Phase 1. The grader requires **three rows** and a keyword such as **Valid**, **Invalid**, or **Boundary**.

Example shape:

```text
TC-01 Valid: GENKI hoodie checkout with 5-char code SAVE2 — format accepted
TC-02 Invalid: GENKI hoodie checkout with 4-char code ABCD — rejected below min
TC-03 Boundary: GENKI hoodie checkout with 10-char code GENKI10MAX — format accepted
```

## Phase 2 — Manual bug hunting

Open the live storefront: **[Sandbox checkout](/sandbox)**.

Hunt at least:

1. **Visual overlap** — on a **narrow viewport** (below 768px), Submit sits on top of CVC. You cannot complete a GENKI payment like a shopper on a phone.
2. **Checkout total logic** — apply **SAVE20** more than once. The discount **stacks** instead of applying once, so the hoodie total is wrong.

Submit **one** report in Phase 2:

- **Severity** and **Priority** (impact vs urgency — [bug lesson](/courses/foundation/03-bug-life-cycle))
- A description of **at least 20 characters** (title, steps, expected, and actual are still the professional bar)

## Phase 3 — Backend and API

### Mock checkout API

`POST /api/checkout` accepts JSON:

```json
{
  "email": "qa@genki.test",
  "promoCode": "SAVE20",
  "items": [{ "sku": "GENKI-HOODIE", "qty": 1 }]
}
```

An **invalid** payload (empty email, empty items, or a promo whose length is not 5-10) must return **400 Bad Request**. Practice that in the [API playground](/api-testing/playground) if you want a Postman-style send.

### Mock schema and SQL

```sql
-- orders
-- id              | user_id | order_status | total_cents | updated_at
-- ord_capstone_9  | 11      | Failed       | 0           | 2026-09-03 16:02:00
```

Write a **SELECT** that verifies the GENKI order landed as **Failed**. The grader requires `SELECT`, `FROM`, and `WHERE order_status = 'Failed'`.

```sql
SELECT id, order_status, updated_at
FROM orders
WHERE order_status = 'Failed';
```

Paste your query into Phase 3.

## Phase 4 — Automation

The Sandbox playground does **not** launch Chrome. Write a spec the same way as [Your First Playwright Test](/courses/ui-automation/02-first-playwright-test): open the sandbox, add a **GENKI hoodie** to the cart, and assert the cart counter.

The grader looks for `page.locator` and `expect(`.

Starter shape (edit in the Monaco editor in Phase 4):

```ts
import { test, expect } from "@playwright/test"

test("GENKI hoodie checkout increases the cart counter", async ({ page }) => {
  await page.goto("/sandbox")
  await page.locator('[data-testid="add-to-cart"]').click()
  await expect(page.locator('[data-testid="cart-count"]')).toHaveText("1")
})
```
