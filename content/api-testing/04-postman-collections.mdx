## What this lesson covers

**Postman** is a client for designing, running, and automating HTTP tests. Used well, it is a living contract: requests, environments, and assertions that Newman can run in CI. Used poorly, it is a folder of unreproducible clicks.

- Collections and folders
- Environments vs collection variables
- The Tests tab as your oracle
- Newman in CI
- How this maps to Quality Central's playground

## Outcome

After this lesson you will be able to sketch a small collection that creates a resource, asserts the contract, and swaps mock vs staging hosts without editing every URL.

## Collections are the suite

A **collection** is a tree of requests. Folders should match **resources**, not random chronology.

```text
Orders API
├── Health
│   └── GET health
├── Orders
│   ├── POST create order
│   ├── GET order by id
│   ├── PATCH status
│   └── DELETE order
└── Negative
    ├── POST invalid body
    └── GET missing id
```

Name requests after the **behavior** (`POST create order`), not after a ticket number.

## Environments vs collection variables

| Store | Use when |
| --- | --- |
| Environment | Host, tokens, and secrets that change per target (mock, staging) |
| Collection variable | Ids produced during a run (`orderId`) |
| Data file | Iteration rows for the collection runner |

Never commit production secrets in a shared collection.

A portable URL looks like this (variables live in Postman, shown here as a fence so lesson MDX stays valid):

```text
GET {{baseUrl}}/api/orders/{{orderId}}
Authorization: Bearer {{token}}
```

`baseUrl` and `token` come from the **environment**. `orderId` is written by a previous request's test script.

<Warning title="Hardcoded hosts rot">
If every request says a literal localhost URL, the collection cannot run in CI against a preview deploy. Variables are what make the suite portable.
</Warning>

## The Tests tab is your oracle

Keep assertions boring and named.

```javascript
pm.test("status is 201", function () {
  pm.response.to.have.status(201);
});

pm.test("order id is a string", function () {
  const body = pm.response.json();
  pm.expect(body.id).to.be.a("string").and.not.empty;
  pm.collectionVariables.set("orderId", body.id);
});
```

Chain GET next:

```javascript
pm.test("fetched order matches created id", function () {
  const body = pm.response.json();
  pm.expect(body.id).to.eql(pm.collectionVariables.get("orderId"));
});
```

That is confirmation plus a contract check. It is also how you stop copy-pasting ids.

## Newman (CI)

```bash
newman run orders.postman_collection.json \
  -e staging.postman_environment.json \
  --reporters cli,junit
```

Fail the pipeline on failed **assertions**, not only on HTTP 5xx. A 200 with the wrong `status` enum is still a failed contract.

## Practical example: `SAVE10` from Postman

1. Environment: `baseUrl` points at the cart API (or Quality Central's dummy API).
2. POST the coupons endpoint with:

```json
{ "code": "SAVE10" }
```

3. Tests: status 200; discount applied once.
4. Duplicate the request. Tests: totals **unchanged** (no stack), or status 409.
5. Export the collection. Run it after every API change.
